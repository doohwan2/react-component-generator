# TDD 규칙

⚠️ **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 프로젝트별 규칙이 이 파일과 충돌하면 프로젝트 규칙을 우선하지만, 그 외에는 아래 내용을 엄격하게 따른다.

---

## 적용 기준

### TDD를 **반드시** 적용해야 하는 대상

- **비즈니스 로직** — 상태 변환, 데이터 처리, 결정 로직
- **API 엔드포인트** — 요청 처리, 응답 형식, 에러 처리
- **유틸리티 함수** — 입력 → 출력 변환, 다항식, 필터링
- **버그 수정** — 재현 가능한 모든 버그는 테스트로 증명 후 수정

### TDD가 **불필요한** 대상

- **타입 정의** (`interface`, `type` 선언만 있는 경우)
- **설정 파일** (`.env`, `vite.config.ts`, `tsconfig.json` 등)
- **순수 UI 컴포넌트** (상태/로직 없이 props를 받아 렌더링만 하는 경우)
- **SQL/ORM 스키마 정의**
- **Enum, 상수 선언**

## RED-GREEN-REFACTOR 사이클

### 🔴 RED: 실패하는 테스트 작성

1. **하나의 동작 = 하나의 테스트** — 각 테스트는 하나의 기능만 검증
   - ❌ 나쁜 예: `test('사용자 가입, 로그인, 주문까지 한다')`
   - ✅ 좋은 예: `test('사용자가 이메일로 가입할 수 있다')`

2. **반드시 실행해서 실패 확인** — 실패한 테스트를 눈으로 본다
   - `npm test` / `bun test` 실행
   - 실패 이유가 명확하게 보여야 함

3. **실패 이유는 "기능 미구현"이어야 함**
   - ✅ 정상: `TypeError: generateReport is not defined`
   - ❌ 비정상: 기존 코드가 깨져서 실패 (이미 구현된 것을 테스트하지 말 것)

4. **테스트 코드만 작성** — 프로덕션 코드는 손도 대지 말 것

### 🟢 GREEN: 최소한의 코드로 통과

1. **"하드코딩"도 괜찮다** — YAGNI 원칙 (You Aren't Gonna Need It)
   - ✅ OK: `return 42` (현재 테스트를 통과하면 됨)
   - ✅ OK: `if (age > 18) return true; return false;`
   - ❌ 아직 할 일 아님: 일반화, 최적화, 패턴 적용

2. **신규 테스트 + 기존 테스트 모두 통과 확인**
   - 새로 작성한 테스트가 통과하는지 확인
   - 기존 테스트가 여전히 통과하는지 확인
   - `npm test` 전체 실행 후 초록색 승인

3. **한 번에 하나의 케이스만 처리** — 다음 케이스는 다음 RED에서

### 🔵 REFACTOR: 중복 제거, 이름 개선, 구조 정리

1. **GREEN을 유지한 채로만** — 테스트가 모두 통과해야 함
   - 모든 테스트를 실행하며 진행
   - 하나라도 빨간색이면 즉시 롤백

2. **새 동작을 추가하지 말 것** — 순수하게 코드 품질만 개선
   - ✅ OK: 함수 추출, 변수명 개선, 중복 로직 통합
   - ❌ 금지: 새 기능, 새 파라미터, 새 분기

3. **다음 동작에 대한 RED로** — 사이클 반복
   - REFACTOR 완료 → RED (다음 테스트) → GREEN → REFACTOR

## 삭제 강제 규칙

**테스트 전에 프로덕션 코드를 먼저 작성했다면 즉시 삭제하고 RED부터 재시작한다.**

- ✅ 정상 흐름: RED (테스트) → 빨간색 확인 → GREEN (코드) → 초록색 확인 → REFACTOR → RED (다음)
- ❌ 위반: 코드를 먼저 작성 → 테스트를 나중에 작성 → 이미 통과함

**"참고용"으로 남기는 것도 금지다.**
- ❌ `// 나중에 쓸 수도 있으니 남겨둠`
- ❌ `// 임시로 이 코드를 주석처리`
- 삭제하고 나중에 필요하면 재작성한다. (Git history에 남음)

## 변명 차단표

| 변명 | 반론 |
|------|------|
| **"너무 단순해서 테스트 불필요"** | 단순할수록 테스트가 빠르다. 단순하면 RED-GREEN이 초 단위로 완료된다. 이 규칙은 단순함을 위반하는 변명이 아니다. |
| **"나중에 추가하겠다"** | 나중은 오지 않는다. 이 사이클을 지금 하고, 다음 동작으로 넘어가라. 기술 부채는 눈덩이가 된다. |
| **"시간이 없다"** | TDD는 느리지 않다. 버그 수정 시간, 통합 테스트 시간, 디버깅 시간을 합치면 더 빠르다. 지금 30초를 투자하거나 나중에 30분을 쏟거나. |
| **"이미 작동하는 코드니까 삭제하면 낭비"** | 코드 낭비가 아니라, 신뢰가 없는 코드를 정리하는 것이다. RED로 증명하고 GREEN으로 구현하면 리팩터링도 안전하다. |
| **"프로토타입이니까 테스트 스킵"** | 프로토타입도 규칙을 따른다. TDD는 프로토타입을 더 빠르게 안전하게 만든다. 프로토타입이 생산 코드가 되면 테스트가 없어서 공중에 떠 있다. |
| **"이건 복잡해서 단위 테스트가 아니라 통합 테스트해야 해"** | 통합 테스트는 단위 테스트 후에 온다. 먼저 단위 테스트로 RED-GREEN을 빠르게 반복하고, 통합 테스트는 추가 검증으로 사용한다. |

## 프로젝트별 규칙 우선 조항

1. **이 파일이 기본값(fallback)이다**
   - 프로젝트 루트 `CLAUDE.md`, `AGENTS.md`에 TDD 규칙이 명시되어 있으면 그것을 따른다
   - 하위 디렉토리 `src/AGENTS.md`, `server/AGENTS.md` 등도 마찬가지

2. **충돌 시 우선순위**
   1. 현재 작업 중인 디렉토리의 `AGENTS.md/CLAUDE.md`
   2. 프로젝트 루트 `AGENTS.md/CLAUDE.md`
   3. 이 `tdd.md`

3. **의존성이 있는 패키지도 확인**
   - 예: Vitest, Jest, Mocha 등 테스트 프레임워크가 명시된 규칙이 있으면 따른다
